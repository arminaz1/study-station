# Study Station, v0.1: Requirements and Test Cases

Status: requirements draft, waiting for answers to the "before you code" questions.
Template for every later stage: Scenario, Requirements, Files, Acceptance checks, Test cases, Git steps, Release note.

## 1. Scenario

A student runs the console program, enters an activity name ("Reading"), then gives a session start and end in seconds (0 and 1500). The program prints the activity name and the session length in seconds. Invalid input is rejected.

Steps:
1. Create an Activity named "Reading".
2. Create a Session for that Activity from start 0 to end 1500.
3. Ask the Session for its duration.
4. main() prints the activity name and the duration.
5. Try invalid input (empty name, end before start, negative start) and confirm each is rejected.

## 2. Requirements

- R1. Activity holds a name. The name must not be empty.
- R2. Session holds: a link to its Activity, a start time, and an end time. Times are int seconds.
- R3. Session start must be 0 or greater. Session end must be equal to or greater than start.
- R4. Session can report its duration in seconds: end minus start.
- R5. Session can report the name of its Activity.
- R6. Activity and Session do no printing, no file access and no device access. All printing happens in main().
- R7. No virtual functions, no interfaces, no templates in this stage.
- R8. The code builds with zero warnings under the flags in section 5 and runs with zero sanitizer reports.
- R9. Times are never taken from a clock. They are passed in as integers.

## 4. Acceptance checks (run these in order)

- A1. Build with the command in section 5. Expected: no errors, no warnings.
- A2. Run the program with the scenario inputs. Expected: it prints "Reading" and 1500.
- A3. Enter an empty activity name. Expected: the program reports the rejection and does not crash.
- A4. Enter end < start. Expected: rejected, no crash.
- A5. Enter start < 0. Expected: rejected, no crash.
- A6. Enter start = end. Expected: accepted, duration 0.
- A7. Run every case in section 6 under the sanitizer build. Expected: no AddressSanitizer or UBSan output.
- A8. grep the core folder for "iostream", "cout", "cin", "fopen", "virtual". Expected: no matches.
- A9. git status shows a clean tree after the tag. git tag lists v0.1.

## 5. Build command

```
g++ -std=c++20 -Wall -Wextra -Werror -pedantic -g -fsanitize=address,undefined \
    src/main.cpp src/core/activity.cpp src/core/session.cpp -o study_station
./study_station
```

## 6. Test cases

How to run in v0.1: no test framework yet (Catch2 arrives in v0.9). You will write a small temporary test file using assert() or a manual console run. Each row below is one check.

| ID  | Input                                | Expected result                           | Kind     |
|-----|--------------------------------------|-------------------------------------------|----------|
| T1  | Activity("Reading")                  | name() returns "Reading"                  | normal   |
| T2  | Activity("")                         | rejected                                  | invalid  |
| T3  | Session start 0, end 1500            | duration is 1500                          | normal   |
| T4  | Session start 600, end 600           | accepted, duration is 0                   | boundary |
| T5  | Session start 900, end 600           | rejected                                  | invalid  |
| T6  | Session start -1, end 10             | rejected                                  | invalid  |
| T7  | Session start 0, end 0               | accepted, duration is 0                   | boundary |
| T8  | Session for "Reading", 0 to 1500     | activity name is "Reading"                | normal   |
| T9  | Session start 0, end 86400           | duration is 86400 (one day)               | normal   |
| T10 | Run T1 to T9 under sanitizer build   | no sanitizer output                       | safety   |

Note: the exact way to report "rejected" depends on answer Q1 below. The expected result must be written in your chosen form before you run the test.

## 7. Git and tooling

### Tools to check (run each and paste the version into chat if something fails)
- `g++ --version`: must be 10 or newer for full C++20 support.
- `git --version`
- `gdb --version`: needed in v0.2, install it now if missing.
- VS Code with the "C/C++" extension (Microsoft).
- Sanitizers need Linux, macOS, or Windows with WSL. Native MinGW on Windows does not support -fsanitize=address. [Likely]

### One-time repo setup
```
cd study-station
git init
git branch -M main
```

Create `.gitignore` with:
```
build/
*.o
*.out
a.out
study_station
*.tmp
```

### Commit and tag at the end of v0.1
```
git add -A
git status                       # check: only intended files are staged
git commit -m "v0.1: Activity and Session classes, console only"
git tag -a v0.1 -m "Activity and Session, console only"
git log --oneline --decorate     # check: the commit shows the tag v0.1
```

### Release note
Create `RELEASE_NOTES.md`. You write the v0.1 entry in your own words: what the release does, what it does not do, and one thing you learned. Commit it in the same commit as the code, before the tag.

### Rules that apply from now on
- One commit per stage. No work-in-progress commits on main after a tag.
- Never edit a committed tag. If v0.1 has a bug, make a fix commit and tag v0.1.1.
- Commit messages start with the version: "v0.x: short description".
